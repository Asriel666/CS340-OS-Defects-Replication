### 分箱约定敏感性分析（2026-11-07 增补，本项目新增分析）

**本节是本项目新增的敏感性分析，不是经验证的论文复现，也不计入 561 项核心对比。**

后续验证原计划"先取得作者分箱脚本或明确的边界、零值及下界处理规则"。在拿到这些规则之前，我们改用敏感性分析把问题收敛：Figure 2 与 Figure 3 的每根柱子都印有精确百分比，已逐项转写为基准（[figure_baselines.json](../reference/figure_baselines.json)，转写值经三系统合计 100% 校验）；再对每种显式约定重算全部序列并与柱标签逐项对比。

固定输入中的关键事实：`line_changes` 恰好落在边界 10/30/50/100 上的记录分别有 40/13/4/1 条；`involved_functions` 落在 3/5/10/30 的分别有 125/54/17/4 条，另有 177 条零函数记录和 7 条 `10+`/`20+`/`30+` 删失记录（全部在 HarmonyOS）；`modified_files` 落在 3/5/10 的分别有 151/53/3 条。因此边界归属必然影响结果，不是理论担忧。

对每种约定（边界 `[lo, hi)` 或 `(lo, hi]`；删失记录按其下界归箱或保持未归属；分母恒为该系统 500 条）重算的结果：

| 序列 | 约定 | 吻合/柱数 | 落在所有箱之外的记录 |
|---|---|---:|---:|
| Figure 2 修改行数 | **`[lo, hi)`** | **15/15** | 0 |
| Figure 2 修改行数 | `(lo, hi]` | 4/15 | 0 |
| Figure 3 涉及函数数 | **`[lo, hi)` + 删失按下界** | **12/12** | 0 |
| Figure 3 涉及函数数 | `[lo, hi)` + 删失未归属 | 11/12 | 7 |
| Figure 3 涉及函数数 | `(lo, hi]` | 0/12 | 177（零函数记录） |
| Figure 3 涉及函数数 | `(lo, hi]` + 删失未归属 | 0/12 | 184 |
| Figure 3 修改文件数 | **`[lo, hi)`** | **12/12** | 0 |
| Figure 3 修改文件数 | `(lo, hi]` | 1/12 | 0 |

吻合按论文两位小数逐柱比较；完整逐柱对比见 [`../results/repair_size/tables/convention_comparison.csv`](../results/repair_size/tables/convention_comparison.csv)，各约定汇总见 [`config_match_summary.csv`](../results/repair_size/tables/config_match_summary.csv)，由 `py -3.11 scripts/run_repair_size.py` 一条命令重算（三次运行语义摘要一致）。

**结论：在已测试的候选中，三个序列只有采用左闭右开口径（末箱含最终上界）、零函数记录计入首箱、删失记录按下界归箱，才能合计得到 39/39 吻合。** 这是一组与柱标签相容的假设，不代表已排除所有其他处理方法。已测试的右闭合实现不能匹配：例如 Android 修改行数 `0-10` 箱论文为 34.0%（170 条），右闭合重算为 37.2%（186 条）；该实现将零函数记录排除在全部箱之外，而分母保持 500，因而各箱比例不再合计为 100%。

**关于论文正文"1–3"的矛盾**：正文把 Figure 3 的集中区间描述为 1–3，这对应 `(0,3]` = {1, 2, 3}。按该口径重算 `0-3` 箱得 Android 73.6%（368 条）、Linux 52.6%（263 条）、HarmonyOS 80.6%（403 条），与柱标签 67.0% / 75.8% / 74.4% 全部不符；只有把 0 计入、把 3 排除的 `[0,3)` = {0, 1, 2} 才逐柱吻合。因此**论文正文描述与自己的图表数据不自洽**，图表数值本身支持"零值计入第一箱"。这也解释了正文口径下右闭合必然失败的原因，前文"正文 1–3 与图不一致"的疑点由此得到数据层面的回答。

两点保留：其一，删失记录“按下界归箱”与论文一致只是**相容**而非证明。`10+` 的真实值仍可能大于 50；把它视为 10、视为同箱内其他值，或直接分配到最后一箱，都可能产生同样柱值，不能据此推断作者实际按 10 处理。HarmonyOS `10-50` 箱的 14 条记录中有 7 条是删失记录（`10+` 3 条、`20+` 2 条、`30+` 2 条），即**这一箱的记录有一半依赖删失处理假设**。保持相同左闭口径、仅将删失处理从“按下界”改成“未归属”，影响的是 **1/12 个函数数柱值**，该柱从 2.8% 降至 1.4%，不是近一半比较项。其二，即使逐柱全部吻合，也仍是统计口径的一致性，不能替代作者分箱脚本的确证。拿到作者脚本后应核对边界、末箱上界和删失处理。

后续验证步骤相应更新：零函数记录与 7 条下界记录仍需查阅公开补丁并保存证据（原始值未做任何改动）；若作者确认分箱脚本，本节敏感性分析即升级为精确复现。

## Figure 4(c)：保留发现的系数差异

[Figure 4(c) 原图](https://arxiv.org/html/2608.20643v1/heatmap-c.png)中 Android–HarmonyOS 的触发场景相关系数为 **0.38**。本次直接从原始标签计数，按以下统一类别顺序对齐：

`Boundary Condition, Concurrency/Multi-thread, Environment Dependency, Multi-Language/Localization, Permission/Identity Dependency, Regular Operation, State Dependency`

| 系统 | 各类别缺陷数量 |
|---|---|
| Android | `[185, 36, 5, 0, 156, 44, 74]` |
| HarmonyOS | `[263, 120, 14, 0, 14, 33, 56]` |
| Linux | `[95, 15, 310, 1, 8, 45, 26]` |

对各向量取升序平均秩，再计算秩的 Pearson 相关，即标准 Spearman：Android–HarmonyOS 为 **0.6126374746329801**，Android–Linux 为 **0.21428571428571427**，HarmonyOS–Linux 为 **0.41443123283995714**。换用数量除以 500 得到的比例不改变秩。HarmonyOS 的两个 14 必须使用并列平均秩，不能任意打破并列。

因此 Android–HarmonyOS 的差异不是两位小数舍入造成的。原因尚未确定：需作者提供 Figure 4(c) 的实际输入及计算代码，才能区分图表誊录、输入版本或算法口径问题。本项目保留原图值与重算值，不修改标签或算法以追求吻合。

## 缺口补齐分析（2026-11-07 增补，本项目新增分析）

**本节所有计算都是本项目新增的探索性分析，不是经验证的论文复现，不计入 561 项核心对比，也不改变任何作者原值。** 由 `py -3.11 scripts/run_gap_analysis.py` 一条命令重算（三次运行语义摘要一致），产物在 `results/gap_analysis/`：Figure 4(c) 口径枚举 `tables/figure_4c_exploration.csv`、Figure 4(d) 候选计算 `tables/figure_4d_candidates.csv`、修复规模异常记录清单 `tables/repair_anomaly_evidence.csv`、机器可读汇总 `tables/gap_analysis_summary.json`。

### Figure 4(c)：常见口径都无法解释 0.38

枚举 3 个维度 × 2 种类别集（保留/去掉三系统全零类别）× 4 种值变换（计数、比例、`log(1+x)`、二值）× 2 种系数（Spearman、Pearson）× 3 个系统对，共 **144 个组合**。对 Android–HarmonyOS 触发场景的 16 个变体，结果只有四个数值：Spearman（计数/比例/log1p）**0.6126**、Pearson（计数/比例）**0.6169**、Pearson（log1p）**0.8048**、二值化 **1.0000**；去掉全零类别不改变任何结果。**没有任何变体接近论文 0.38，最小绝对差为 0.2326。**

把搜索范围扩到全部 144 个组合（检验"跨维度/跨系统对誊录错位"假说），落在 0.38±0.02 的只有 4 项，且全部是"受影响功能维度 × Android–HarmonyOS × Pearson 计数/比例"的 **0.3606**（该格论文值为 0.43），按两位小数仍不吻合。因此常见口径变换、类别集调整、改用 Pearson、乃至简单的图表错位都不足以解释差异；更可能是作者使用了不同输入版本或不同计算代码。差异仍保持不吻合记录，需作者提供 Figure 4(c) 的实际输入与脚本。

### Figure 4(d)：候选定义均不能复现原图

在保留"未确认"状态的前提下，把论文没有定义的 Overall 输入显式枚举为 6 种向量构造（拼接计数/比例/log1p/二值、每维平均秩拼接、按类别数加权）× 2 种系数，外加 2 种逐维聚合（三个维度 rho 的均值/中位数），共 **42 个候选**。与原图 `-0.11 / 0.05 / -0.04` 相比，最接近的是"按类别数加权 + Pearson"，三对平均绝对差 **0.0930**；其次为"逐维 rho 均值"0.1046、"拼接计数/比例 + Pearson"0.1243。全部远大于两位小数吻合阈值。

**没有任何候选定义能复现 Figure 4(d)**，这从数据侧支持了本项目把 Overall 标为未确认的决定。正文把 -0.11 归给 Linux–Android 与图中位置的矛盾也未消解。所有 42 行的状态均为 `unconfirmed_candidate`，需作者给出输入向量、拼接方式、权重与系统对标注后再补独立基准、计算和测试。

### Figures 2/3：异常记录的结构化证据清单

导出 177 条零函数记录与 7 条 `10+`/`20+`/`30+` 删失记录，共 **184 行**（`results/gap_analysis/tables/repair_anomaly_evidence.csv`），逐行保留原始标签、规范化值、增删行数、修改文件数、补丁 URL 与域名，并预留 `patch_accessible`、`verified_function_count`、`reviewer_evidence`、`adjudication` 四列供人工填写。补丁域名集中在 `android.googlesource.com`、`bugs.launchpad.net`、`gitee.com`。

本地交叉验证：177 条零函数记录中 **81 条**涉及多个修改文件、**10 条**修改行数 ≥50、**9 条**同时满足；按系统为 Android 18、Linux 145、HarmonyOS 14。这些子集信号更接近"函数数未记录"而非"真实零函数修改"，但多数零值记录仍是单文件、较小改动，**数据不足以判定**。自动清单只是把待核查对象结构化，不等于已阅读补丁；本项目没有访问任何补丁 URL、没有改动原值，也不宣称完成了人工复核。

因此 Figures 2/3 的状态仍为"分箱口径已被 39/39 逐柱吻合所收敛、但作者脚本未确证"：本轮补齐的是证据清单与差异搜索，**精确复现仍需作者的分箱脚本，以及逐条补丁核实**。
